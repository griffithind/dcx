# dcx

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)
[![Go 1.27](https://img.shields.io/badge/Go-1.27-00ADD8.svg)](https://go.dev/)

A single-binary CLI for [devcontainers](https://containers.dev/): no Node.js,
and every editor connects over SSH.

- **Any editor**: a small SSH server runs in the container; VS Code, Zed,
  Cursor, Neovim or plain `ssh` connect to it, with agent forwarding.
- **Compatible**: reads `devcontainer.json`, features and
  `devcontainer-lock.json` like the official CLI
  ([differences](docs/compatibility.md)).
- **Secrets from your password manager**, fetched on the host and mounted as
  files.
- **Smart rebuilds**: recreates only when the config, a Dockerfile or a
  compose file changes.

## Install

Requires Docker Engine, the `docker compose` plugin and an OpenSSH client.

```bash
curl -fsSL https://raw.githubusercontent.com/griffithind/dcx/main/install.sh | sh
```

This installs `~/.local/bin/dcx` after checking it against the release's
`checksums.txt`. Run it again to upgrade. To build from source, run
`make build` (writes `bin/dcx`) or `make install` (copies it to
`$(go env GOPATH)/bin`). `go install` does not work: the agent binaries dcx
embeds are generated by `make build`.

## Quick start

```bash
cd myproject
dcx up                    # build, start, configure SSH, run the hooks
dcx ssh                   # shell in the container
dcx ssh -- npm test       # run a command
ssh myproject.dcx         # or any SSH client
```

The SSH host is `<name>.dcx`, from `name` in devcontainer.json (or
`<workspace id>.dcx` without one); `dcx status` shows it.

- **VS Code / Cursor**: install Remote - SSH, run "Remote-SSH: Connect to
  Host" and pick the host.
- **Zed**: "projects: Open Remote" and connect to the host.

After a reboot or a Docker restart, run `dcx up` again: it starts the
container, fetches the secrets, starts the SSH server and runs
`postStartCommand` (the once-only hooks don't run again). Until then the
host refuses connections.

## Trust

`dcx up` runs commands from the repository **on your host**:
`initializeCommand` and the `customizations.dcx` secret commands. Only run it
in repositories you trust, and read those fields first in an unfamiliar one
(`dcx config --raw` prints the config as written).

## Commands

| Command | Description |
|---------|-------------|
| `dcx up` | Create or start the devcontainer. `--recreate`, `--rebuild` (rebuild images), `--pull` (re-pull the base image and re-fetch features; with `--recreate` for an existing container), `--hosts` (see [SSH access](#ssh-access)) |
| `dcx down` | Remove the containers, the SSH host entry and the host key. `--volumes`, `--remove-orphans` |
| `dcx stop` | Stop the containers. `-f`/`--force` ignores `shutdownAction: "none"` |
| `dcx restart` | Stop, then `up` (which recreates if the config changed). `-f`/`--force`, `--rebuild` |
| `dcx ssh [-- cmd]` | Shell or command over OpenSSH, the same session as `ssh <host>` |
| `dcx status` | State, SSH host and endpoint, why a container is stale. `-d`/`--detailed` (host key, plan, features, labels), `--json` |
| `dcx list` (`ls`, `ps`) | Running environments. `--all`, `--json` |
| `dcx logs` | Container logs. `-f`/`--follow`, `--tail N` (default 100), `-t`/`--timestamps` |
| `dcx build` | Build the images without starting. `--no-cache`, `--pull` |
| `dcx clean` | Remove unused dcx images and the `~/.dcx` folders of workspaces without a container. `--current`, `--all`, `--dangling`, `--dry-run` |
| `dcx lock` | Write or check `devcontainer-lock.json`. `--verify`, `--frozen` (CI), `--json` |
| `dcx config` | devcontainer.json after substitution, as JSON. `--raw`, `--validate` |
| `dcx doctor` | Check Docker, the config and the running workspace's SSH server. `--system`, `--config-only`, `--json` |
| `dcx completion <shell>` | bash, zsh, fish or powershell completions |

Global flags: `-w`/`--workspace`, `-c`/`--config` (relative to the current
directory), `-v`/`--verbose` (also prints the docker commands), `-q`/`--quiet`
(no progress or warnings), `--no-color` (also off with `NO_COLOR` or off a
terminal).

Data goes to stdout and progress to stderr, so `dcx list --json | jq` sees
only data. JSON keys are camelCase; with `--json` a failure is
`{"error": "..."}`.

## Configuration

dcx reads `.devcontainer/devcontainer.json`, `.devcontainer.json` or
`.devcontainer/<name>/devcontainer.json` (or `--config`; such a config is
its own environment), with `image`, `build` (Dockerfile) or
`dockerComposeFile`.

### Secrets

```json
{
  "customizations": {
    "dcx": {
      "secrets": { "DATABASE_URL": "op read op://Dev/db/url" },
      "buildSecrets": { "NPM_TOKEN": "op read op://Dev/npm/token" }
    }
  }
}
```

Each value is a command run on the host; its output is the secret.

- **`secrets`** are files at `/run/secrets/<name>` on a tmpfs (never on
  disk), mode 0400, owned by `remoteUser`, else `containerUser`, else root.
  They are fetched again on every `up`. To export them in shells:
  `for f in /run/secrets/*; do [ -f "$f" ] && export "$(basename "$f")=$(cat "$f")"; done`
  in `~/.bashrc` (the `-f` test skips dcx's own `/run/secrets/dcx` folder).
- **`buildSecrets`** are BuildKit secrets for Dockerfile and compose builds
  (`RUN --mount=type=secret,id=NPM_TOKEN …`), never stored in a layer.

### Features and lockfile

Features come from OCI registries (`ghcr.io/devcontainers/features/node:1`,
a tag and/or `@sha256:…`), local folders inside `.devcontainer`, or HTTPS
tarballs (`devcontainer-feature-<id>.tgz`). Legacy short ids (`"node"`) are
mapped with a warning. They install as root in the official CLI's order.
Private registries use `$DEVCONTAINERS_OCI_AUTH`, your `docker login`
credentials (including `credHelpers`, `credsStore` and identity tokens), or
`$GITHUB_TOKEN` for ghcr.io.

Fetched features are cached in `~/.cache/dcx/features` (`$XDG_CACHE_HOME`).
Tags are checked again after 24 hours, and the cached copy is used when the
registry is unreachable; `--pull` re-fetches everything.

`dcx lock` writes `devcontainer-lock.json` (`.devcontainer-lock.json` for a
`.devcontainer.json`) in the official CLI's format, pinning each registry or
tarball feature to its digest. `up` and `build` then fetch by those digests,
and write the lockfile themselves only when it is an empty file. Commit it,
and run `dcx lock --frozen` in CI.

### Lifecycle hooks

`initializeCommand` runs on the host on every `up`, before anything else.
`onCreateCommand`, `updateContentCommand` and `postCreateCommand` run once
per container, `postStartCommand` on every start, and `postAttachCommand` at
the start of each interactive SSH session. `up` waits for all of them
(`waitFor` has no effect), so start long-running processes in the
background. A hook is a string (`sh -c`), an array, or an object of named
commands run in parallel. Image metadata's hooks run first, then the
features', then devcontainer.json's. Container hooks run over SSH, on a
pseudo-terminal when dcx runs in a terminal.

### Workspace, ports and users

- **Workspace**: the git repository containing the workspace is mounted at
  `/workspaces/<repository>`, and the default `workspaceFolder` is the
  workspace's place in it. `workspaceFolder` only sets the working
  directory; `workspaceMount` moves the mount (`""` for none). Compose
  configs mount it in the compose file.
- **Ports**: `forwardPorts` without a host address and `appPort` numbers
  publish on `127.0.0.1`; `appPort` strings are passed to Docker as written.
  Ranges work (`"8000-8005:3000-3005"`). A port listed twice, or already
  published by the compose file, is published once.
- **Environment**: `containerEnv` is set on the container (and written to
  `/etc/environment`); `remoteEnv` only reaches sessions and hooks.
- **Users**: sessions run as `remoteUser`, else `containerUser`, else the
  image's user, with the container's `SHELL` or the user's login shell.
  With `updateRemoteUserUID` (the default on Linux) that user's UID/GID is
  changed to yours, so bind-mounted files have the right owner.

### Names and SSH access

The container and compose project are named `<name>-<workspace id prefix>`,
so two checkouts never collide. Each workspace's SSH entry answers to
`<name>.dcx` (unless another workspace already uses it) and always to
`<container>.dcx`, which is unique and stable.

dcx keeps its own workspace id, labels and project names, so dcx and VS
Code's "Reopen in Container" on one folder are separate environments.

<a id="ssh-access"></a>The SSH server accepts only your keys (`~/.ssh/*.pub`,
your SSH agent's, and dcx's fallback key in `~/.dcx`), on a loopback port
chosen at create time. `up --hosts`
(`10.0.0.0/24`, `any`, `loopback`) widens which addresses may connect; it is
kept until a `--recreate` changes it. Where Docker proxies published ports
(Docker Desktop, rootless), every client appears to come from the gateway.

## Files dcx writes

| Path | Contents |
|------|----------|
| `~/.dcx/` (`$DCX_HOME`) | `known_hosts`, a fallback client key, and `workspaces/<id>/`: host key, lock, compose override, `workspace.json` |
| `~/.ssh/dcx/config` | SSH host entries, included from the top of `~/.ssh/config` (`$DCX_SSH_DIR` replaces `~/.ssh`) |
| `~/.cache/dcx/features` | Fetched features |
| `devcontainer-lock.json` | Written by `dcx lock` |

Container state lives in Docker labels (`com.griffithind.dcx.*`); images are
tagged `dcx/<workspace id>:…`.
